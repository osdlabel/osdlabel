## Document format

osdlabel uses a flat JSON array format for persisting annotations:

```json
[
  {
    "id": "ann-1",
    "imageId": "sample-1",
    "contextId": "general",
    "geometry": {
      "type": "rectangle",
      "origin": { "x": 100, "y": 200 },
      "width": 300,
      "height": 150,
      "rotation": 0
    },
    "rawAnnotationData": {
      "format": "fabric",
      "fabricVersion": "7.4.0",
      "data": { ... }
    },
    "createdAt": "2026-03-06T12:00:00.000Z",
    "updatedAt": "2026-03-06T12:00:00.000Z"
  }
]
```

### Mask annotations

Annotations painted with the [segmentation
brush](/osdlabel/guides/segmentation-brush/) carry pixels rather than a vector
shape, so they use a different `rawAnnotationData` envelope. Their `geometry` is
a **summary** — a bounding box and an exact pixel count — and the pixels
themselves live in the payload:

```json
{
  "id": "ann-2",
  "imageId": "sample-1",
  "contextId": "general",
  "toolType": "segmentationBrush",
  "geometry": {
    "type": "mask",
    "origin": { "x": 140, "y": 80 },
    "width": 230,
    "height": 200,
    "pixelCount": 33192
  },
  "rawAnnotationData": {
    "format": "osdlabel-mask",
    "data": {
      "x": 140,
      "y": 80,
      "width": 230,
      "height": 200,
      "imageWidth": 600,
      "imageHeight": 800,
      "counts": "URLNASDBASq4..."
    }
  },
  "createdAt": "2026-03-06T12:00:00.000Z",
  "updatedAt": "2026-03-06T12:00:00.000Z"
}
```

`counts` is base64 of LEB128 run lengths, row-major over the bounding box and
starting with a run of background. This is osdlabel's own encoding, not COCO —
see [Exporting masks in another format](#exporting-masks-in-another-format).

`pixelCount` is the exact number of set pixels, so it is always at most
`width * height` — validation rejects a larger one. The payload may also carry
an optional `fill` recording the mask's tint; the built-in `Annotator` does not
write one, leaving the colour to the renderer.

### Masks at a downsample

A mask may be stored coarser than the image: with `downsample: d`, each stored
**cell** stands for a `d`×`d` block of image pixels. The brush starts new
masks at `d` = 1. A stroke refines an existing mask at its own `d`, or
re-grids it finer when the view is close enough. In a context whose
`brush.maxDownsample` is above 1, a stroke that outgrows the cell cap coarsens
the mask instead of being refused. Only the run grid
changes; everything a reader uses to place the mask stays in image pixels:

```json
"geometry": {
  "type": "mask",
  "origin": { "x": 240, "y": 160 },
  "width": 120,
  "height": 80,
  "pixelCount": 9600,
  "downsample": 4
},
"rawAnnotationData": {
  "format": "osdlabel-mask",
  "data": {
    "x": 240, "y": 160, "width": 120, "height": 80,
    "imageWidth": 1280, "imageHeight": 800,
    "counts": "ANgE",
    "downsample": 4
  }
}
```

The grid conventions, which every reader and writer shares:

- **`downsample`** is a power of two from 1 to 2¹⁶. A missing field means 1,
  and 1 is never written, so a full-resolution payload is byte for byte what it
  was before the field existed. The `format` string stays `osdlabel-mask`.
- **The box and the geometry are in image (level-0) pixels** at every
  downsample. `counts` runs row-major over the box's `ceil(width / d)` ×
  `ceil(height / d)` cells.
- **The box is cell-aligned.** `x` and `y` are multiples of `d`, and so are its
  right and bottom edges (`x + width`, `y + height`), except where those are
  the image's own edges. A payload that breaks this is skipped on import.
- **Cell `(cx, cy)` covers** image pixels `[cx·d, min((cx+1)·d, W))` ×
  `[cy·d, min((cy+1)·d, H))`, where `W`×`H` is the image: cells are counted
  from the image origin, so the box's first cell is `(x / d, y / d)`. Cells in
  the last column or row of an image whose side is not a multiple of `d` are
  clipped by the image edge.
- **`pixelCount`** is the exact number of image pixels the mask covers, with
  clipped edge cells counted at their clipped size, so `area()` needs no
  knowledge of `d`.
- **Pixel-centred formats need a shift.** A cell's centre is at
  `cx·d + (d − 1) / 2` in coordinates where image pixel `i` is centred on `i`,
  so an export to OME-Zarr 0.6 (which centres pixels) carries a scale of `d`
  and a translation of `(d − 1) / 2`.

### How large a mask may be

A mask's box may hold at most 64 Mi **cells** (`MAX_MASK_PIXELS`,
`ceil(width / d) · ceil(height / d)`), so a coarser mask can cover a larger
region. The bound is the format's, not one reader's: the validation schema
enforces it, `deserialize` skips a mask past it (whatever `maxMaskPixels`
says — larger values are clamped), and it is checked on write too —
`encodeCanonical`, `createMaskAnnotation` and `maskAnnotationFields` throw
`MaskCapacityExceededError` rather than produce a payload every reader would
refuse.

## Exporting annotations

Use `serialize()` to create a flat array of annotations from the current state:

```tsx
import { serialize } from '@osdlabel/solid';

const { annotationState } = useAnnotator();

const doc = serialize(annotationState);
const json = JSON.stringify(doc, null, 2);

// Save to file, send to API, etc.
```

## Importing annotations

Use `deserialize()` to parse an array and load it into the store:

```tsx
import { deserialize } from '@osdlabel/solid';

const { actions } = useAnnotator();

const parsed = JSON.parse(jsonString);
const { byImage } = deserialize(parsed);
actions.loadAnnotations(byImage);
```

`deserialize()` checks a document in three steps, the cheap one first:

1. Before it decodes any mask, it checks what each annotation declares against itself, with `OsdAnnotationCrossFieldSchema` from `@osdlabel/validation`: that its `geometry.type` and the kind of its `rawAnnotationData` agree ([below](#geometry-and-the-saved-fabric-object)), and that its `toolType` draws that geometry ([Choosing a `toolType`](#choosing-a-tooltype)).
2. It converts mask payloads written in another format and decodes every mask (see [Importing](/osdlabel/guides/segmentation-brush/#importing) in the Segmentation Brush guide).
3. It checks every annotation whole with `OsdAnnotationSchema` (see [Validation](#validation)).

If any annotation fails step 1 or step 3 it throws `SerializationError`, whose message names the first problem that step found, and returns nothing, so a bad document is never half loaded. A mask whose pixels cannot be decoded is the one exception: it is dropped alone and listed in the result's `skipped`. Because step 1 comes first, an annotation whose declared geometry disagrees with its payload or its `toolType` refuses the document even when its own pixels could not be decoded either, a document that is refused there costs no decode at all, and the refusal names that disagreement even when an earlier annotation is missing a field, which step 3 would have reported. Step 2 recomputes a mask's geometry from its pixels, so step 1 is the only point at which the geometry a mask declared is checked: under a mask payload it must be a mask geometry, or be omitted ([below](#geometry-and-the-saved-fabric-object)). Omitted, it counts as a mask geometry, so the annotation still needs `toolType: 'segmentationBrush'`, and under another tool it refuses the document whatever its pixels. The decode bounds `maxMaskPixels` and `maxTotalMaskPixels` (see [Importing](/osdlabel/guides/segmentation-brush/#importing)) are checked before step 1: an invalid one, `NaN` say, throws whatever the document holds.

### Flat out, keyed in

The two directions are intentionally **asymmetric**, and it trips people up:

- **`serialize(state)` returns a flat `Annotation[]`** — and so does the `onAnnotationsChange` callback (see [below](#listening-to-changes)). That flat array **is** your persistable document; you can save the callback's argument directly without calling `serialize` yourself.
- **`deserialize(doc)` returns a keyed `{ byImage }` map** — `Record<ImageId, Record<AnnotationId, Annotation>>` — which is the exact shape `loadAnnotations` expects for the store.

So: persist the **flat** array, load it back through `deserialize` to get the **keyed** map. If you keep your own annotation list (e.g. a flat `Annotation[]` from `onAnnotationsChange`), you still pass it through `deserialize` to seed the store.

### Geometry and the saved Fabric object

Every vector annotation stores its shape twice, and each copy is authoritative for something different:

| Field               | Authoritative for                                                                                              |
| ------------------- | -------------------------------------------------------------------------------------------------------------- |
| `rawAnnotationData` | What is painted on the canvas, and what the user selects, drags, resizes and rotates                           |
| `geometry`          | What is measured and labelled, what `boundingBox` and `centroid` read, and the shape hosts read from an export |

When the user draws or edits a shape, both fields are written together from the same Fabric object: an edit recomputes `geometry` from the edited object. So the two agree in everything the annotator saves, except in data saved by releases up to 0.21.0: their rectangles ([below](#rectangles-saved-by-earlier-releases)), and the rectangles and circles they let the user skew or stretch ([below](#rectangles-and-circles-saved-skewed-or-stretched)).

A document edited by hand or written by another tool can pair them wrongly. `deserialize` rejects an annotation whose saved Fabric object is not the class that paints its geometry's type:

| `geometry.type`   | Fabric class in `rawAnnotationData.data.type` |
| ----------------- | --------------------------------------------- |
| `rectangle`       | `Rect`                                        |
| `circle`, `point` | `Circle`                                      |
| `line`            | `Line`                                        |
| `polyline`        | `Polyline`                                    |
| `polygon`         | `Polygon`                                     |

A mask is the exception. Its `rawAnnotationData` is an `osdlabel-mask` pixel payload, not a Fabric object ([Mask annotations](#mask-annotations)), and the pixels are authoritative for both: `deserialize` recomputes a mask's `geometry` from them. A mask geometry with a Fabric payload, or a vector geometry with a mask payload, is rejected:

```text
Validation failed: Annotation "m1" has mask geometry, but its rawAnnotationData is a "fabric" payload, not "osdlabel-mask"
```

This is checked on the fields as the document writes them, before the mask is decoded and its geometry recomputed, and every payload that is not Fabric counts as a mask payload: a mask exported through a codec ([below](#exporting-masks-in-another-format)) may not declare a vector geometry either. Under a vector geometry the message names the payload's format and the one the geometry needs, since a format that is not `"fabric"` may as well be a misspelling of it (`"Fabric"`) as a mask's:

```text
Validation failed: Annotation "a1" has rectangle geometry, but its rawAnnotationData's format is "coco-rle", not "fabric"
```

A mask payload may omit its `geometry`, since decoding supplies one, but a geometry it declares must be a geometry. One that is not, such as `null`, a string, `{ "type": "Rectangle" }`, or `{ "downsample": 4 }` (a mask geometry needs its `"type": "mask"`, whatever else it records), is refused with a message saying what it is, which quotes nothing of it but a string `type`, cut short. The message calls the payload a mask payload, since that is how the rule counts it, and quotes its format, so a misspelled `"fabric"` shows there:

```text
Validation failed: Annotation "m1" has a mask payload (format "coco-rle"), but its geometry is an object whose type is "Rectangle", not a mask geometry
```

Fabric saves the class name capitalised, as above; the lowercase name, which Fabric also loads, is accepted too. The error names the annotation and both types:

```text
Validation failed: Annotation "a1" has rectangle geometry, but its rawAnnotationData is a Fabric Circle, not a Rect
```

`deserialize` cannot tell whether the saved object sits where the geometry says: that needs Fabric to rebuild the object, and `deserialize` is synchronous. An annotation whose two fields describe the same kind of shape in different places loads as saved. It is painted from `rawAnnotationData`, measured from `geometry`, and its geometry moves to the painted shape the first time the user edits it.

So don't pair the two fields by hand. Build annotations with [`createAnnotationFromGeometry`](#seeding-from-external-geometry), which writes both from one geometry. If you change an annotation's geometry outside the annotator, rebuild it the same way, with its `id`, `toolType`, `label` and style, rather than editing `geometry` alone. `loadAnnotations` and `initialAnnotations` check neither field, so pass data from outside your app through `deserialize` first.

### Rectangles saved by earlier releases

Up to 0.21.0, a rectangle was painted centred on the corner its geometry records, half its size up and to the left of where it was drawn. Fabric 7 places an object by its centre unless told otherwise, and the rectangle tool never told it. Rectangles are now painted where their geometry says.

A rectangle's `origin`, `width` and `height` are its box before rotation, and `rotation` turns that box about its centre, so the centre is always `origin + (width / 2, height / 2)`. Those releases read `origin` back from the shape as the centre it was painted at, so that is what a rectangle saved by them holds. On a rectangle never edited, that point is also the top-left corner of the drag; after a move, resize or rotation it is only the centre.

A rectangle saved by an earlier release still paints where users saw it, because its saved Fabric data is what is drawn. Its geometry is loaded as saved, though, so its measurements, labels and exports sit half its size from the shape on screen. The geometry is corrected the first time the rectangle is edited, because it is read back from the shape's centre.

`deserialize` does not change it. To correct such rectangles when you load them, pass each annotation through `migrateLegacyRectangle`, which recomputes the geometry of an earlier release's rectangle from where it is painted and returns any other annotation unchanged:

```ts
import { deserialize, migrateLegacyRectangle } from '@osdlabel/solid'; // or '@osdlabel/react'

const { byImage } = deserialize(JSON.parse(jsonString));
for (const annotations of Object.values(byImage)) {
  for (const annotation of Object.values(annotations)) {
    annotations[annotation.id] = migrateLegacyRectangle(annotation);
  }
}
actions.loadAnnotations(byImage);
```

It is a separate module that nothing else imports, so a bundle that does not use it does not include it. It is also importable on its own as `@osdlabel/fabric-annotations/legacy-rectangle`. It recognises an earlier release's rectangle by Fabric data with a centre origin whose `left` / `top` match the geometry's `origin`, to within the rounding Fabric applies when it saves.

### Rectangles and circles saved skewed or stretched

Up to 0.21.0, the select tool's handles could make a shape its geometry cannot describe. **Shift** with a side handle sheared a rectangle into a parallelogram, or a circle into a slanted ellipse, and a circle's side handles, or **Shift** with a corner, stretched it into an ellipse. The geometry kept the rectangle about the same centre, unsheared, or a circle of the larger radius, while the saved Fabric data kept the shape on screen. The handles no longer do either.

Such an annotation loads as saved: it still paints the sheared or stretched shape, and its geometry is what it was. The first time it is edited (moved, resized or rotated), its Fabric data is replaced with data that paints its geometry, in the same style, and the shape on screen snaps to what its measurements, labels and exports already described. Nothing changes it on load, and there is no migration helper for it.

### Points saved with a scaled or slanted dot

A point's dot is always drawn at its style's radius, the `radius` its Fabric `Circle` was saved with. A point saved with a scale or a skew on that `Circle` loads as saved, like the shapes above: it still paints the dot it saved, larger, smaller or slanted, until its next edit redraws it at that radius. Its geometry is only its position, which the saved `Circle` agrees with, so its measurements, labels and exports are unaffected.

## Exporting masks in another format

`serialize` takes an optional codec that re-encodes mask payloads on the way
out. Vector annotations pass through untouched:

```ts
import { serialize, deserialize, createMaskCodecRegistry, cocoRleCodec } from 'osdlabel';

const coco = serialize(annotationState, { maskCodec: cocoRleCodec });

// Reading it back needs a registry of the codecs you might encounter.
const registry = createMaskCodecRegistry(cocoRleCodec);
const { byImage } = deserialize(coco, { maskCodecs: registry });
```

Without `maskCodec`, masks keep the canonical `osdlabel-mask` encoding, which
round-trips exactly. Note that `{ maskCodec: cocoRleCodec }` produces osdlabel
annotations whose mask payloads are COCO RLE — it does **not** produce a COCO
dataset document. Writing your own codec, the `pycocotools` interop caveat for
very large images, and what survives a round trip are all covered in the
[Segmentation Brush guide](/osdlabel/guides/segmentation-brush/#exporting).

## Seeding from external geometry

Loading already-serialized osdlabel documents is just `deserialize` (above). The harder case is **importing annotations from another system** — you have raw geometry (a bounding box from a detector, a contour from a segmentation model, points from a CSV) but no Fabric `rawAnnotationData` envelope.

Use `createAnnotationFromGeometry` — it builds the complete annotation (geometry **and** the Fabric envelope) in one call:

```tsx
import { createAnnotationFromGeometry } from '@osdlabel/solid'; // or '@osdlabel/react'

const annotation = createAnnotationFromGeometry(
  { type: 'rectangle', origin: { x: 120, y: 80 }, width: 200, height: 140, rotation: 0 },
  { imageId, contextId, toolType: 'rectangle', label: 'lesion' },
);

actions.addAnnotation(annotation);
```

It accepts any `VectorGeometry` (`rectangle`, `circle`, `line`, `point`, `polyline`, `polygon`), defaults the style to `DEFAULT_ANNOTATION_STYLE`, generates an `id` when you don't supply one, and guarantees the `id` survives serialization — so, given a `toolType` that draws the geometry ([below](#choosing-a-tooltype)), the result round-trips through `serialize` / `deserialize` like a hand-drawn annotation. To seed many at once, map over your source data and call `loadAnnotations` (or `addAnnotation` per item).

### Choosing a `toolType`

`toolType` records which tool drew the annotation, and constraints count annotations by it: a context's limit on rectangles counts the annotations whose `toolType` is `'rectangle'`. Pass a tool that draws your geometry's type. For most shapes that is the tool of the same name. A path has two, because the polyline and freehand tools each draw an open path or close one:

| `toolType`          | Resulting `geometry.type`                         |
| ------------------- | ------------------------------------------------- |
| `rectangle`         | `rectangle`                                       |
| `circle`            | `circle`                                          |
| `line`              | `line`                                            |
| `point`             | `point`                                           |
| `polyline`          | `polyline` (open path) or `polygon` (closed path) |
| `freeHandPath`      | `polygon` (closed path) or `polyline` (open path) |
| `segmentationBrush` | `mask` ([Seeding a mask](#seeding-a-mask))        |

`deserialize` rejects any other pairing. Loaded, an annotation recorded under another tool would count against that tool's limit and free a place in its own: a rectangle recorded as `'line'` would use up one of the context's lines. The error names the annotation, its geometry type, its `toolType` and the tool types that draw it:

```text
Validation failed: Annotation "a1" has rectangle geometry, but its toolType is "line", not "rectangle"
```

`createAnnotationFromGeometry` does not check the pairing, so an annotation built with another one is stored and counted as given, and its document is then refused when it is loaded.

The static `toolTypeToGeometryType` helper returns one type per tool, `polyline` for both `'polyline'` and `'freeHandPath'`, but at runtime the polyline tool draws a closed `polygon` when the path is closed, and the freehand **tool** draws a closed `polygon` by default (an open `polyline` only when Shift is held). When importing a freehand contour, set `geometry.type` to whichever matches your data and pass `toolType: 'freeHandPath'`.

Multi-point shapes import the same way: pass `{ type: 'polyline', points }` (open) or `{ type: 'polygon', points }` (closed), where `points` is an array of image-space `{ x, y }` coordinates. Annotations drawn with the built-in freehand tool are already plain `polygon` / `polyline` geometry, so there is nothing special to handle when importing them either.

### Seeding a mask

Masks are the one geometry `createAnnotationFromGeometry` cannot build — its
parameter type is `VectorGeometry`, so passing a mask is a compile error rather
than a runtime surprise. A mask's geometry is only a bounding-box summary; the
pixels are separate, so there is nothing to build from geometry alone.

Paint the pixels into a buffer and use `createMaskAnnotation`:

```ts
import { BoundedDenseMaskBuffer, createMaskAnnotation } from 'osdlabel';

const buffer = new BoundedDenseMaskBuffer({ imageWidth: 600, imageHeight: 800 });
for (const [x, y] of foregroundPixels) buffer.set(x, y, 1);

actions.addAnnotation(
  createMaskAnnotation(buffer.snapshot(), { imageId, contextId, label: 'lesion' }),
);
```

If your source is already COCO RLE, decode it instead of replaying pixels — a
`MaskSnapshot` is exactly what `createMaskAnnotation` takes. `decode` is
optional on `MaskCodec` (an export-only format may omit it), so narrow before
calling:

```ts
import { cocoRleCodec, createMaskAnnotation } from 'osdlabel';

const { decode } = cocoRleCodec;
if (decode) {
  actions.addAnnotation(createMaskAnnotation(decode({ size, counts }), { imageId, contextId }));
}
```

Importing a whole document of them is
[`deserialize(doc, { maskCodecs })`](#exporting-masks-in-another-format).

### Lower-level escape hatch

If you already hold a **Fabric object** (of a supported class) rather than raw geometry, you can build the envelope directly instead of going through `createAnnotationFromGeometry`:

```ts
import {
  getFabricOptions,
  serializeFabricObject,
  getGeometryFromFabricObject,
  buildFabricObjectFromGeometry,
} from '@osdlabel/solid';

// From an existing Fabric object → annotation pieces:
const rawAnnotationData = serializeFabricObject(obj); // envelope
const geometry = getGeometryFromFabricObject(obj, 'polygon'); // image-space geometry

// Or the inverse — geometry → Fabric object (what createAnnotationFromGeometry uses internally):
const fabricObject = buildFabricObjectFromGeometry(geometry, getFabricOptions(style, id));
```

These read/produce the same five Fabric classes (`Rect` / `Circle` / `Line` / `Polyline` / `Polygon`). `buildFabricObjectFromGeometry` and `createFabricObjectFromRawData` also give a rectangle or circle the handles the library gives them (side handles that only scale on a rectangle, uniform corners only on a circle), which Fabric does not save; if you revive an annotation's object some other way, such as `deserializeFabricObject`, and put it on a canvas, call `applyShapeControls(obj, geometry.type)` first. The annotation `id` is registered automatically when an `Annotator` mounts; if you build and serialize Fabric objects entirely outside any viewer, call `initFabricModule()` once first so the `id` survives `toObject()`. (`createAnnotationFromGeometry` guarantees this for you regardless.)

## Validation

The library provides comprehensive Valibot schemas for annotation validation in the `@osdlabel/validation` package:

```tsx
import * as v from 'valibot';
import { BaseAnnotationSchema } from '@osdlabel/validation';

if (v.safeParse(BaseAnnotationSchema, unknownData).success) {
  // unknownData is basically valid BaseAnnotation
}
```

Validation checks include:

- Required string fields (`id`, `imageId`, timestamps)
- Geometry type and shape validation
- Numeric bounds checking (coordinates, dimensions)
- Extension fields (when composed into a custom schema)
- That a mask geometry has a mask payload, and a vector geometry a Fabric one (`OsdAnnotationSchema`, which is what `deserialize` uses)
- That the saved Fabric object is the class that paints the geometry's type (also `OsdAnnotationSchema`; see [above](#geometry-and-the-saved-fabric-object))
- That the `toolType` is a tool that draws the geometry's type (also `OsdAnnotationSchema`; see [Choosing a `toolType`](#choosing-a-tooltype))

`OsdAnnotationCrossFieldSchema` runs the last three checks alone, on an entry as written: it is what `deserialize` runs before it decodes any mask ([Importing annotations](#importing-annotations)). It counts every payload that is not Fabric as a mask payload, and holds that payload's geometry, which decoding replaces, to a mask geometry or none. Any other field that is missing or of the wrong type it leaves to `OsdAnnotationSchema`. Every entry it refuses, `OsdAnnotationSchema` would refuse as written too, so it never refuses an entry `OsdAnnotationSchema` accepts as written. It does not replace it: it lets a mask payload omit its geometry and does not check a mask geometry's numbers, which decoding supplies.

## Listening to changes

The `onAnnotationsChange` callback fires whenever annotations are added, updated, or deleted:

```tsx
<AnnotatorProvider
  onAnnotationsChange={(annotations) => {
    // annotations: Annotation[] — the same flat document serialize() would produce.
    // No need to call serialize() yourself; persist this array directly.
    saveToBackend(annotations);
  }}
>
  {/* ... */}
</AnnotatorProvider>
```

## Annotations that cannot be rendered

`deserialize` validates the Fabric payload in each annotation's `rawAnnotationData`, including its object type, that type's key fields and that the type matches the geometry's, so a document that passes it will almost always render. Annotations passed to `loadAnnotations` or `initialAnnotations` aren't validated, though, so they can hold a payload Fabric can't rebuild: one that is malformed, or names a class your build doesn't register.

Such an annotation is skipped on the canvas and stays in state, and every other annotation on the image still renders. Its decorations, such as labels and measurements, are derived from its geometry rather than from the canvas object, so they still appear where the shape would be. By default it is reported with a `console.warn` naming the annotation and its image. Pass `onAnnotationRenderError` to handle it yourself:

```tsx
<AnnotatorProvider
  onAnnotationRenderError={({ annotation, error }) => {
    // annotation: the skipped Annotation; error: what rebuilding it threw.
    reportToMonitoring(`Annotation ${annotation.id} could not be rendered`, error);
  }}
>
  {/* ... */}
</AnnotatorProvider>
```

`<Annotator>` takes the same prop. It is called once per skipped annotation, each time the image's annotations are rebuilt. If your handler throws, the error is logged with `console.error` and the other skipped annotations are still reported.

## Getting all annotations

Use `getAllAnnotationsFlat()` to extract a flat array from the state at any time:

```tsx
import { getAllAnnotationsFlat } from '@osdlabel/viewer-api';

const { annotationState } = useAnnotator();
const allAnnotations = getAllAnnotationsFlat(annotationState);
```
